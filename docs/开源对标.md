## 2. 优秀项目如何让流程持续运转

### NovelForge：产物可被后续工作流消费

README 描述 Schema 驱动卡片、字段生成与校验、上下文引用 DSL、知识图谱、代码式工作流和项目初始化模板。关键不是“有很多按钮”，而是上一阶段产生有类型的卡片，下阶段可以稳定引用；审核和实体状态提取先预览，再确认写入。

**采纳：** 蓝图、章纲、正文和记忆分工明确；AI 产物先成为提案。
**本版不做：** 通用 Schema 编辑器、代码式工作流 Agent、知识图谱引擎。把它们直接搬入 Studio 会重复 Mira 的运行时职责，也超出首版需要。

### QMAI：草稿不等于正式事实

README 描述总纲→卷纲→章纲、写前上下文包、正式章节后的记忆摄取、版本化快照和多维审查，并强调未确认草稿不能污染正式记忆。它的细纲模板具有自己的类型偏好，不应成为所有小说的固定文学规则。

**采纳：** 当前章节之前的有效记忆才供后章使用；正文修改令旧摘要失效；定稿需要作者确认。
**本版不做：** 固定卷/故事节拍、向量+全文混合检索、复杂角色状态与多轮自动修复。Studio 当前只有作者维护设定和带来源指纹的章节摘要，不能叫完整记忆引擎。

### Show Me The Story：小批规划与逐章验收

使用说明建议先配置规则与人物，再生成小批章纲，审阅确认后写作，单章读过并接受后再推进；还区分事实提取、设定变更提案、最终校对与备份恢复。作者可以调整方向而不必预先固定全书。

**采纳：** “全书方向粗、近期章节细”；章节焦点贯穿规划、写作和审阅；对比后逐段选择。
**本版不做：** 单独部署 Go 服务、导入续作、校对撤回与备份恢复。Mira 负责持久化与未来恢复契约。

### AI-Novel-Writing-Assistant：规划、执行和恢复有不同边界

README 描述创作约定→世界/角色→近期规划→授权写作范围→上下文→正文→检查→局部修文/复验→保存→角色/资源/伏笔状态回流；还明确暂停后的处理入口、预算和运行记录。持续创作需要状态和恢复语义，不能靠重复点“生成”。

**采纳：** 模型生成不自动落稿；展示实际上下文；错误不伪装成功，保存和生成各自有状态。
**本版不做：** 自动导演、多阶段后台任务、并行代理、运行预算和断点恢复。当前 Studio 只有单次完整文本请求草案，不能向用户承诺后台跑完整本书。

## 3. 共性结论

| 需要解决的问题 | 共性的产品机制 | Studio 本版落点 |
| --- | --- | --- |
| AI 不知道下一步做什么 | 阶段与输入/输出明确 | 蓝图→规划→正文→审阅→记忆 |
| 越写越偏 | 本章目标与全书规则可引用 | 上下文预览、章纲与写作约定 |
| 候选污染正式内容 | 生成与采纳分离 | 待审阅提案、段落选择、基线校验 |
| 旧事实影响新章 | 来源、时间边界和版本有效性 | 前章过滤、来源指纹、改稿失效 |
| 出错后盲目重试 | 持久化、执行与确认分开 | dirty/error、串行保存；远端恢复待宿主 |
| 作者被流程绑死 | 全局方向稳定，近期可改 | 可直接写正文，允许回改蓝图 |

## 4. 下一阶段正确顺序

先和 Mira 明确并实现最小宿主 SDK，再验收“真实保存→生成提案→采纳→确认记忆→下一章引用”的闭环。闭环稳定后才评估专项审稿、按需检索、复杂状态和批量生成。需要后台执行时由 Mira 暴露任务接口；Studio 不内嵌第二套 Agent 或驱动框架。
