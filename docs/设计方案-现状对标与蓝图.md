# Mira Novel Studio 设计方案：现状盘点 · 对标分析 · 蓝图

> 2026-09-30 · 基于对 Mira-Harness 内置 aiNovel 模块的通读，以及对同类开源项目/商业产品的网络调研。
> 定位：按 PRODUCT.md 的规划，小说创作将从 Harness 内置页面升级为独立维护的 Mira Novel Studio 应用（仍走 Electron 宿主的受控平台能力）。

---

## 一、现状盘点（Mira-Harness 内置 aiNovel）

代码范围：`src/pages/frontend/aiNovel/**`（约 900 行）、`src/config/novel.ts`、`electron/{adapters,ipc,storage,preload}/novel*.ts`。

### 1.1 数据模型（`src/config/novel.ts`）

`NovelProjectDocument v1` 是单一 JSON 文档：

| 领域 | 现状 |
|------|------|
| 作品设定 story | 5 个自由文本字段：背景 / 人物 / 角色 / 关系 / 剧情核心 / 写作风格 |
| 故事总纲 outline | 单个字符串，全作只有一份 |
| 章节 chapters | 扁平数组，每章仅 `title / outline / content` 三个字符串 |
| 知识库 knowledge | 平铺条目：分类 + 标题 + 内容 + 标签 |
| 思维导图 mindMap | 仅根节点 + 一级子节点标题列表（无可视化） |
| 提示词 prompts | 4 个内置模板（总纲/章节/正文/选区润色），可增删 |
| 其他 | assistantMessages、generatedIdeas、optimizer（模式+迭代数）、splitterSource |

存储：better-sqlite3 单表 `novel_projects`，整个项目 JSON 全量读写；前端 deep watch + 600ms 防抖全量上传。

### 1.2 AI 管线

- 两个模型角色：`authoring`（创作）/ `automation`（批量处理），OpenAI 兼容 SSE，由 Electron 本地代理转发（`electron/adapters/novelApi.ts`），实际取的是 Harness 统一模型配置（`database.models`）。
- 上下文构造 = `buildContext()` 全量字符串拼接：标题 + 5 个设定字段 + 总纲 + 当前章 + **全部知识库条目**，塞进单条 user message。
- 无对话历史回传（assistantMessages 只存不用）、无中断（AbortController 未透传到 UI）、无重试、无 token 预算、无采样参数控制。
- 已有 AI 能力：生成总纲 / 章节细纲 / 正文 / 继续创作 / 章节标题 / 书名简介 / 导图节点 / 拆书 / 批量优化；选中文本右键 → 润色 / 扩写 / 去除 AI 味。

### 1.3 UI 结构

- 三栏：ProjectSidebar（224px：作品列表 + 阶段导航 + 章节列表）｜ EditorWorkspace（阶段 tabs：设定→总纲→章节细纲→正文）｜ AiPanel（280px：快捷动作 + 输出文本框 + 自由提问 + 工具入口）。
- 编辑器：设定字段支持 markdown/rich 切换（rich 用 Milkdown Crepe）；**总纲、细纲、正文都是原生 `<textarea>`**——`NovelMarkdownEditor`（Milkdown）已封装好却只用在设定字段上。
- 工具抽屉：知识库 / 提示词模板 / 思维导图 / 书名简介 / 拆书 / 批量优化 / 快捷词条。
- 导出 JSON / MD / TXT，导入 JSON。
- 首页有「从模板开始」入口，实际 `openTemplates()` 是 `ElMessage.info('模板功能暂未开放')` 占位。

### 1.4 遗留问题

- 设置页 `backend/aiNovel/index.vue` 仍在维护旧的 endpoint/apiKey/modelId 三元组（`NOVEL_MODEL_PROFILES_PREFERENCE_KEY`），而运行时已改走 Harness 模型配置 + `workspaceSettings.modelSelection`，属于双轨遗留（配套还有 `legacyNovelApiAuth.ts`）。
- 拆书/批量优化的结果与原稿之间只有"整框文本 + 整体应用"，没有 diff 与部分采纳。
- 思维导图只是一列输入框，没有图渲染。

## 二、核心差距分析

对标对象：AI 长文生成类开源项目、成熟写作软件（novelWriter / manuskript / bibisco 等）、商业 AI 写作产品（NovelCrafter / Sudowrite / NovelAI、阅文作家助手等）的公开设计。逐层对比后的差距如下，按影响排序：

### G1. 结构模型太浅：章 ≠ 场景（影响：长篇组织能力）

成熟写作工具普遍以 **场景（scene）为最小写作单元**，层级为 卷/幕 → 章 → 场景（novelWriter、manuskript、NovelCrafter 均如此）。场景才有：视角人物、地点、出场角色、时间标记。v1 的扁平章节数组撑不起 100+ 章、多线叙事的书；也无拖拽排序、无章节状态（草稿/定稿）、无卷册概念。

### G2. 设定没有实体化：无法精确注入与守护一致性（影响：长篇一致性）

人物/世界观是两个自由文本字段。成熟做法是**实体卡片库**（角色：外貌/性格/口癖/关系/成长弧线；地点、组织、物品、规则条目），并支持：
- 在正文里 `@引用` 实体，被引用的实体自动进入当次生成的上下文（NovelCrafter 的 Codex 模式、NovelAI 的 Lorebook）；
- 实体与章节建立"出场关系"，做一致性审校（人物名前后不一、已死角色再出场）。
v1 的知识库虽是雏形，但全量注入、无关联、无分类视图，本质是"带标签的记事本"。

### G3. 上下文引擎缺失：全量拼接不可扩展（影响：成本与质量）

`buildContext()` 把全部设定+知识库无差别塞入单条 prompt：
- 30 章以后正文 prompt 轻松超过多数模型窗口，或成本失控；
- 不感知"本章出场了谁、发生了什么"，注入的是静态全量而非动态相关；
- 没有"前情提要"机制（前章结尾原文 / 滚动摘要），续写连贯性全靠模型硬扛。
对标项目普遍做了：相关性检索（关键词/向量）→ 预算裁剪 → 分层注入（设定摘要 / 相关实体卡 / 前情摘要 / 本章细纲）。

### G4. AI 产出没有审阅与安全网（影响：用户信任）

生成/优化/拆书都是"结果整体覆盖"或"追加到末尾"：
- 无 diff 审阅、无部分采纳、无逐段取舍；
- 无版本快照 / 历史记录 / 回收站，AI 覆盖性操作一旦应用不可回退；
- 生成不可中断，失败无重试，网络抖动即前功尽弃。
商业产品（Sudowrite / NovelCrafter）把"AI 提议 → 人工审阅 → 增量采纳"做成核心交互；开源工具普遍有快照或与 git 集成。

### G5. 单轮单候选：没有迭代空间

- 每次生成只有一个结果，不满意只能重跑覆盖；没有多候选并排对比挑选；
- AiPanel 有"自由提问"，但请求不带任何历史，是金鱼式对话；
- prompt 是模板字符串硬拼接，没有结构化组装层（system / 设定 / 检索块 / 任务 / 约束分段），既难调优也难调试。

### G6. 编辑器基础能力薄弱（影响：日拱一卒的写作体验）

正文是 textarea：无字数目标与进度、无打字机/专注模式、无查找替换、无批注、无自动保存冲突保护；已引入的 Milkdown 没有用在正文上。novelWriter 的自动高亮（引号/重复用词）、字数统计目标、manuskript 的卡片式大纲都是低成本高感知的对齐点。

### G7. 产品闭环缺口

- 模板库占位未实现（题材模板：玄幻/都市/悬疑…，含预设设定字段与提示词）；
- 无写作统计（日/周字数、进度、码字热力图）；
- 无导入现成 TXT 小说（解析分章），拆书只支持粘贴到抽屉；
- 导出无 EPUB / 分卷导出；
- 无伏笔/剧情线追踪面板。

### 3.3 跨项目共性：成熟项目普遍做了、v1 完全没有的 12 件事

1. **分层生成流水线**：设定→总纲→卷纲→章纲→场景 Beats→正文，每层产物可查看可编辑（v1 只有 总纲→章纲→正文 三层且产物不可独立管理）。
2. **写后状态回灌 / 章节记忆摄取**：每章定稿后自动提取"本章改变了什么"（角色状态、关系、伏笔、时间线）写回全局状态。v1 只读不写，从不更新。
3. **一致性审校独立环节 + 独立模型**：writer/editor 分离，审校不通过可否决。
4. **伏笔全生命周期**（埋设→提醒→回收，超期异常标记）。
5. **检索式长程记忆**：向量/BM25/图谱混合检索，超越"最近 N 章"窗口；注入带预算与优先级。
6. **生成候选确认制 / 草稿与正史分离**：AI 产出先落草稿态，确认才写入并触发记忆摄取；多候选对比。
7. **待确认事实与既成事实分离**：防止 AI 把假设写成既定设定。
8. **拆书 / 风格蒸馏 / 去 AI 味**三件套（中文网文刚需，v1 只有最简拆书和"去 AI 味"按钮）。
9. **断点续跑 / 任务可恢复**：批量生成可暂停、可恢复、失败主动停下。
10. **Diff 审批 + 版本快照 + 自动 git/快照**。
11. **提示词资产化**：可编辑、可版本化、带注入 DSL（v1 的 prompts 已有雏形但无注入机制）。
12. **成本可观测**：token/费用实时显示、预算守卫。

### 3.4 差异化机会（竞品的共同短板）

- **流程太重、依赖用户纪律**：QMAI 作者自认"提取记忆这步最容易被忽略，漏了整个系统失效"；NovelForge 工作流易校验失败。→ **把记忆摄取、一致性检查做成默认自动（可关）**，是明确的差异化机会。
- **缺少简单/进阶分层**：多数竞品一上来就是全套流水线，新手劝退。→ 简单模式（写作+伴写）与进阶模式（全流水线）可切换。
- **工程可靠性参差**：macOS 适配差（QMAI 未公证）、迁移不稳（NovelForge v0.9）、无 CI。Mira 有成熟的宿主与存储基础设施可依赖。

## 四、Mira Novel Studio 设计蓝图（草案）

### 4.1 定位与设计原则

Mira Novel Studio 是独立微应用（Wujie 接入，Electron 宿主持有模型、存储与文件能力），区别于 Harness 内置版的三个定位升级：

1. **从"生成器"到"工作台"**：AI 是伴写者，产出必须经过审阅才能落稿；人始终拥有稿件的最终控制权。
2. **从"单文档"到"结构化长篇"**：以场景为最小单元管理百万字级项目。
3. **从"全量上下文"到"上下文引擎"**：设定实体化 + 按需检索 + 预算控制，让第 1 章和第 120 章获得同样高质量的 AI 支持。

原则：本地优先（数据不出本机，模型调用走用户配置）；人机分工明确（AI 提议、人决策）；每一层生成产物都可重跑、可回退、可部分采纳。

### 4.2 信息架构

```
首次进入 → 全屏引导（① 笔名与称呼 → ② 按模块分配模型 → ③ 欢迎；可跳过，之后从首页设置图标重进）
首页（活动总览 + 书架）
  ├─ 问候行：接下来写点什么，{称呼}？+「继续《上次作品》」+ 设置入口
  ├─ 创作总览（Claude 式活动面板）：累计字数 / 今日字数 / 写作天数 / 连续写作 / 高产时段 / 常用模型
  │    + 近 15 周写作热力图 + 一句对比（≈ N 本《活着》）
  ├─ 书架（网格 / 列表双视图，偏好持久化）：模板封面卡 / 状态 / 字数 / 进度
  └─ 作品工作台（位置记忆：恢复上次编辑的场景）
       ├─ 写作区（默认）：场景编辑器 + 右侧 AI 伴写栏 + 顶部上下文条
       ├─ 编排区：卷/章/场景树 + 卡片式细纲板 + 剧情线/伏笔时间轴
       ├─ 设定区：角色卡 / 世界观条目 / 关系图 / 知识库
       └─ 审阅区：AI 产出审阅队列、版本历史、一致性检查报告
```

- 首次引导的模型分配按 **模块**（正文创作 / 大纲与细纲 / 摘要与提取 / 审校检查）而非全局单模型——对标 AI_NovelGenerator 的任务级模型路由（草稿用快模型、定稿用强模型）；生成请求携带按模块路由选出的 modelId。
- 顶部上下文条：始终显示"本次生成将注入什么"（设定摘要 · 相关实体 N 条 · 前情提要 · 本章细纲），点击可展开编辑——把 G3 的黑盒变成可见可控的。
- AI 伴写栏：常驻右侧（可折叠），承载续写/扩写/对话式迭代/多候选卡片；选中文本就地出现内联操作（改写/扩写/缩写/换说法），结果以 diff 预览。

### 4.4 AI 管线 v2

**上下文引擎**（对应 G3；分层模型参考 QMAI 的 11 层上下文包与 NovelAI 的固定层+近端层结构）：

1. 组装分层（按优先级）：`system（创作规范+文风） → 用户手动指定 > 本章细纲/场景 Beats > 上一章结尾原文（K 字） > 滚动摘要链（前情） > 相关实体卡（按 characterIds/aliases 匹配） > 伏笔状态 > 佳作参考`，每层 token 上限 + 总预算，超限按优先级裁剪；实时显示"约 xx token / 窗口 xx"。
2. 实体注入三档开关（NovelCrafter 模式）：每条实体可设 `Always / 仅被提及时 / Never`，默认「仅被提及」；别名自动识别正文提及。
3. 滚动摘要链：每章定稿自动生成 ≤200 字摘要进入前情链（Sudowrite Chapter Continuity 模式）——成本极低，是长篇连贯性的地基。
4. **Prompt 预览**：发送前可查看完整拼装结果（NovelCrafter "Preview final prompt"），把上下文从黑盒变成可见可控的调试界面。

**记忆回灌（写后摄取）**（调研共性 #2，v1 完全缺失的最大机制缺口）：

- 每章标记定稿时，用 automation 模型（便宜模型即可）自动提取：本章摘要、出场角色及其状态/关系变化、伏笔埋设/回收、时间线推进 → 以**提案形式**呈现 → 用户确认后写回实体库与状态表（默认自动确认可关，但提案始终可追溯）；
- 草稿与正史分离：草稿阶段的正文不污染记忆库，只有定稿才触发摄取（QMAI 原则）；
- 记忆条目带来源章节引用，可跳转原文（KazKozDev 的溯源思想）。

**审阅流**（对应 G4）：

- 所有"覆盖性"操作（生成正文/优化/拆书导入）先落审阅队列：diff 视图（段落级对齐）+ 逐段采纳/丢弃/再生成；应用前自动存快照（对照 goink 的 Diff 审批流）；
- 生成可中断（AbortController 透传 UI），失败自动重试一次，错误态可一键重发；
- 长任务（整卷批量生成）可暂停/恢复，失败主动停下报告而不是无限重试。

**多候选与迭代**（对应 G5）：

- 关键生成（正文段、章纲）支持 2-3 候选并排卡片（彩云小梦三选一模式），选一采纳或拼装；
- 伴写栏对话保留近 N 轮历史；支持"再来一版，更压抑一点"式迭代；
- prompt 组装结构化（分块拼装器），每块可在设置中查看/覆盖，提示词是可版本化的产品资产（v1 prompts 的进化方向）。

**任务级模型路由与成本可观测**（调研共性 #3、#12）：

- 按任务分配模型：草稿/摘要/提取用便宜快模型，正文/审校用强模型（复用 Harness 的 authoring/automation 双角色，可扩展为 按任务覆盖）；
- 一致性审校用独立模型角色（writer/editor 分离），审校结论可否决定稿；
- 每次生成显示 token 用量与估算费用，作品级用量面板。

### 4.5 编辑器与写作体验（对应 G6/G7）

- 正文升级为 Milkdown（已有依赖与主题适配）：标题/引用/分隔线满足网文排版即可，避免过度富文本；
- 打字机模式 / 专注模式、字数目标与日更进度、查找替换、自动保存 + 冲突提示；
- 章节树拖拽排序、状态标记（idea/outline/draft/done）与进度徽标；
- 模板库：题材模板（含预设实体字段模板、默认提示词组、示例章节结构）；
- 统计面板：日/周字数、各卷进度、码字热力图；
- 导入 TXT 长文（按章回正则分章）→ 进入拆书流程生成细纲；导出增加 EPUB、分卷导出。

**开书选题：频道 / 分类 / 标签**（对标番茄作家开书流程，2026-10-08 实地调研）

番茄的开书顺序：封面 → 书名 → 签约模式（连载/完本）→ 目标读者（男频/女频）→ 阅读标签（主分类必选单一 + 主题/角色/情节各≤2，签约后不可改）→ 内容标签（情节≤4 / 情感≤2 / 人设≤2 / 世界观≤1）→ 主角名 → 简介。背后是两套体系：**阅读标签**面向读者分类与搜索，**内容标签**面向平台推荐。

我们的翻译（差异在最后一条，是关键）：

1. **频道**：男频 / 女频 / 通用（不限）——决定分类库与默认情感基调；作者自由切换。
2. **主分类**（单选）：**男频 19 / 女频 21 直接采用番茄全量**（西方奇幻/东方仙侠/悬疑灵异/战神赘婿/宫斗宅斗/豪门总裁/青春甜宠…）；通用 6 个为本工作室补充（悬疑推理/规则怪谈/无限流/科幻未来/现实向/冒险）。
3. **标签组**（全量转载番茄两套体系合并去重，共 470 个，原始快照 `docs/reference/fanqie-taxonomy.json`）：
   - 题材主题 96（男/女频「主题」∪ 内容标签「世界观」）· 主角人设 128（「角色」∪「人设」）· 情节走向 190（「情节」∪「情节」）· 情感基调 56（「情感」）
   - 跨组去重规则：世界观/设定类归题材主题，角色原型归主角人设，情节装置归情节走向，关系动态归情感基调
   - 限选预算对齐番茄两套体系之和后收敛：**题材 ≤3 · 人设 ≤4 · 情节 ≤4 · 情感 ≤2**；UI 折叠每组前 14 个（已选置顶）+ 搜索框 + 展开全部，470 个标签不压垮向导。
4. **标签驱动生成（与番茄的本质区别）**：番茄的标签是喂推荐系统的元数据；我们的每个分类/标签携带**生成预设包**——实体字段模板、提示词组、节奏协议、**一致性检查规则**，在创建作品时预填进实体库与提示词，后续注入上下文与审校。这是"标签即配置"：选题不是装饰，是生成引擎的输入。

| 标签示例 | 生成预设（M4 模板库填充内容） | 一致性规则示例 |
|---------|------------------------------|----------------|
| 系统 | 预填「系统」概念卡（面板规则、任务机制） | 面板数值与能力边界前后一致 |
| 追妻火葬场 | 节奏协议：误会→决裂→追悔→挽回 | 挽回阶段不得跳过主角成长弧线 |
| 扮猪吃虎 | 身份暴露节奏建议写入章纲 | 暴露节点不超过计划章数 |
| 无CP | system 层禁忌：不发展情感线 | 审校检查情感线描写越界 |
| 规则怪谈 | 预填「规则条目」概念卡组 | 已立规则自洽（后文不得违反） |

5. **AI 按内核推荐标签**（规划）：填完一句话内核后，automation 模型按内核推荐频道/分类/标签，用户采纳或调整。

**封面（开书阶段的四档选择，对标番茄「选择封面」弹窗）**：

番茄封面弹窗实测：两个 tab——「本地上传」（600×800 像素，jpg/png/jpeg ≤5MB，审核 1-2 小时）+「模板封面」（固定 15 个 canvas 模板，书名与笔名注入设计，点选打勾）。我们的翻译：

1. **纯色板书名封面**（无需素材，随开书即得）：书名竖排衬线字 + 色板由书名哈希稳定生成——同一本书在任何设备上颜色一致；书架整齐，零成本。
2. **模板封面**（9 套，`styles/covers.scss`）：覆盖番茄模板的视觉家族——水墨/描金/留白/青绿/桃夭/绛红/橄榄/墨绿，另加夜蓝（悬疑科幻补充）；**书名实时注入模板设计**，向导内 5 列画廊点选（对齐番茄网格交互）。技术选型：CSS 渲染（非 canvas），用容器查询单位（cqw/cqh）让同一模板在书架 76px 与预览 118px 间等比缩放，另天然获得明暗主题适配。**长书名自适应：绝不截断**——排版加宽（基础封面按书名长度 2→5 字/行，竖向模板自动添列）+ 实测字号微调（逐档下降字号直到完整落入封面，含 1px 舍入容差），30+ 字书名也能完整落版。
3. **上传图片并裁剪**（M4）：3:4 封面比例，内置裁剪器（拖拽构图、可重新调整、可移除回书名封面）；**图片二进制存宿主应用资源目录，项目文档只存 assetId**。
4. **AI 生成封面**（规划中，M4+）：按题材 + 一句话内核 + 风格蒸馏资产生成封面图，生成结果同样落为 image 资源；本期只预留入口与数据结构，不写实现。

封面出现在三处：书架卡片、工作台标题区、导出 EPUB 的封面首图。

### 4.6 一致性守护（差异化方向）

- 实体识别：automation 模型（或本地正则 + aliases 匹配）扫描正文，标记出现的人物/地点，**自动**反哺场景卡的 characterIds——默认自动执行，不依赖用户纪律（这是相对 QMAI/NovelForge 的核心差异化）；
- 一致性检查报告：定稿前跑一轮"本章 vs 设定库"审校（人物性格越线、已死角色出场、时间线矛盾、待确认事实被写成既成事实），产出问题清单而非直接改稿；
- 伏笔登记簿：伏笔条目（埋设章节 → 目标回收章节 → 状态：埋设/提醒/回收），超过目标章节未回收标黄提醒（goink 的超期异常机制）；
- 风格蒸馏（可选进阶）：贴入样文，从句式/用词/修辞/节奏/叙事距离/氛围六维蒸馏出"文风资产"，可绑定到作品注入 system 层（goink/QMAI 模式）；
- 双模式分层：**简单模式**（写作 + 伴写 + 自动摘要链，不强制任何流程）与**进阶模式**（完整流水线 + 摄取确认 + 审校门禁）可切换——多数竞品缺失的新手路径。

### 4.7 技术选型与复用

沿用：Vue 3 + Element Plus、Milkdown（正文主编辑器）、better-sqlite3、Electron 本地 SSE 代理（novelApi 模式可平移）；模型接入复用 Harness 统一模型配置，删除 legacy 双轨配置页。

新增（建议）：diff 渲染用 `diff-match-patch` 或 `fast-diff`；场景树拖拽用 `vue-draggable-plus`；EPUB 导出用 `epub-gen`/`jszip`；长程检索第一阶段用关键词 + aliases 匹配 + SQLite FTS5，第二阶段可引入 `sqlite-vec` + 本地量化嵌入模型（goink 已验证完全离线路线，bge-small-zh int8 约 30MB）；⚠️ 对标项目多为 AGPL-3.0，只借鉴机制设计，不复制代码。
